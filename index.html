    UniCommerce → Zoho Books & Inventory

    Every marketplace and website order is fulfilled from a third-party warehouse running UniCommerce. Five scheduled Deluge jobs follow each order through its whole life and post the matching documents in Zoho, so finance never re-keys an order and stock stays true.

    Jobs5 scheduled functions
    Volume~250 orders a day
    AuthOAuth token + Zoho connection
    SafetyDedup, dry run, run caps

    Orders become Books sales orders

    POST uc/oms/saleOrder/search → POST books/salesorders → POST …/status/open
    • Pulls CREATED, PROCESSING, COMPLETE and CANCELLED orders in a rolling window and caches existing Books orders by number first.
    • Orders already in Books only get a status refresh, and are skipped when the status hasn't changed.
    • Cancellations older than 15 days are treated as settled and cost zero API calls.
    • Customers are created only when missing. Marketplace orders map to one marketplace customer.
    • Place of supply comes from the billing or shipping state, normalised to GST state codes.
    • A pre-create guard re-checks Books right before every POST.
    uc_to_books_sales_orders.dg
    
    
    
    
    
      
    
        
    Dispatches move physical stock
    
        
    GET getShippingPackageDetails + shippingManifest  →  custom module  →  books/packages + shipmentorders
    
        
      
          
    • Each UniCommerce package is stored in a Books custom module with its status, dispatch date, invoice number and an items table.
      • 
          
    • The dispatch date comes from the shipping manifest, with a fallback chain, never "today".
      • 
          
    • Only dispatched statuses create a Books package and shipment, which reduces physical stock. Accounting stock moves with the invoice.
      • 
          
    • Packable quantity is checked per sales-order line, which avoids Books error 36012 on split shipments.
      • 
          
    • Pagination stops on has_more_page, with a page list built without range() or while, which Deluge doesn't have.
      • 
        
    
      
    
      
    uc_shipments_to_module.dg
    
    
    
    
    
      
    
        
    Invoices with the right GST
    
        
    POST uc/invoice/details/get  →  GET books/settings/taxes  →  POST books/invoices
    
        
      
          
    • Works from shipment records not yet invoiced, checking the sync flag before parsing dates to stay under Deluge statement limits.
      • 
          
    • Org tax rates are cached once per run into GST group and IGST lookups keyed by percentage.
      • 
          
    • Intra-state lines get the GST group, inter-state lines get IGST, and marketplace freight carries no tax.
      • 
          
    • A missing SKU stops that invoice as a data gap instead of posting a partial document.
      • 
          
    • The UniCommerce invoice number is stored on the record so the invoice is never created twice.

    Payments that match the courier
    
        
    POST uc/invoice/details/get  →  saleorder/get (delivery date)  →  POST books/customerpayments
    
        
      
          
    • UniCommerce is the source of truth for amounts. The Books balance only caps what is applied.
      • 
          
    • Prepaid amounts are booked at once. COD is booked only after delivery, dated with the real delivery date.
      • 
          
    • Returned or RTO packages never get a COD receipt.
      • 
          
    • Records dated before the Zoho go-live are flagged as synced, since Books rejects them (error 2042).
      • 
          
    • Dedup on reference number and a per-record payment-synced flag make runs resumable.

    uc_payments_to_books.dg
    
    
    
    
    
      
    
        
    Returns become credit notes and refunds
    
        
    POST uc/return/search (RTO, RECEIVED)  →  books/creditnotes  →  …/invoices  →  …/refunds
    
        
      
          
    • Rolling 7-day window by updated date, so the scheduler never needs manual dates.
      • 
          
    • Warehouse QC is read per unit: BAD units are not restocked, unscanned units are held, good units return to stock.
      • 
          
    • Shipping and COD charges are credited too. Shipping GST follows place of supply.
      • 
          
    • The credit note is applied to the invoice up to its balance, which cancels the unpaid COD part.
      • 
          
    • Any prepaid remainder is refunded by bank transfer. Dedup on the return invoice code.

    Engineering decisions
    Simulate an orderSimulate an order»
    
    
    
      
    Problem
    A cached lookup and a slow create left a window where the next run created the same order again. 86 duplicate sales orders slipped through.
    Fix
    A live pre-create guard right before every POST, plus Books' own duplicate code (36004) treated as a skip.
    
      
    Problem
    Status changes like DISPATCHED → DELIVERED re-ran the item aggregation and hit the Deluge statement limit.
    Fix
    Decide whether a Books shipment is needed before doing any item work. Only real transitions pay the cost.
    
      
    Problem
    The shipment prefetch reached into the future and cached ~14,800 records each run.
    Fix
    Prefetch only backwards from today, enough to catch order-to-ship drift. Cache stays small.
    
      
    Problem
    COD money was booked when the invoice was raised, so receivables looked paid before the courier collected.
    Fix
    COD is booked on delivery with the delivery date. RTO packages never get a receipt.
    
      
    Problem
    Books refuses documents dated before the migration, so old records failed on every run.
    Fix
    A migration cutoff flags them as synced once, and they drop out of the working set.
    
      
    Problem
    Deluge has no while loop or range(), but the APIs paginate up to hundreds of pages.
    Fix
    A generated page list with early exit on has_more_page, and caps on new records per run.

    POST qb/chainSalesTransactionTracker  →  books/invoices  →  customerpayments  →  creditnotes + refunds

    POST qb/fetchPurchaseOrdersWithDetails  →  books/purchaseorders  →  …/status/open  →  inventory/purchasereceives

    Stock moved between stores
    
        
    POST qb/storeStockTransactionTracker  →  inventory/transferorders  →  …/intransit  →  …/markastransferred

    What it handles
    Post a sample billPost a sample bill»
    
    
    
      
    Problem
    POS totals are rounded at the counter, so Books invoices came out a few paise off and stayed part-paid.
    Fix
    After create, the difference to the payable amount is written as a rounding adjustment.

    Lines are aggregated per item before the transfer order is built.

    Stock equaliser physical = accounting
    
      
    Zoho keeps two stock figures for every item. Accounting stock moves with invoices and bills; physical stock moves with shipments and receives. When integrations, returns or manual entries leave them apart, this solution closes the gap by creating the missing shipments and receives, item by item and location by location, until physical stock matches accounting stock.
    
      
    
        
    ReadBoth stock figuresPer item, per location
    →
        
    Physical higherShipmentSales order → package → shipment, no invoice
    →
        
    Physical lowerReceivePurchase order → receive, no bill
    →
        
    ResultGap = 0Accounting stock untouched
    
      
    
      
    
        
    Direction
    Physical above accounting: ship the excess out. Physical below: receive the shortfall in.
    
        
    Books impact
    No invoices or bills are raised, so accounting stock, revenue and payables stay exactly as they were
    
        
    Level
    Works at item and location level, the same way Zoho tracks stock

    Purchase Ident Form inside Zoho Books
    
      
    Books has no purchase-request document, so I built one: a custom module with an item table, and a web-tab widget the team uses to raise requests without leaving Books. It loads customers and items through a Books connection and writes one new record per submit.
    
      
    
        
    Module
    Custom module with an auto-number (PIF-1, PIF-2…), customer lookup, dates, status, discount and tax %, notes
    
        
    Item table
    A Books table field with item lookup, quantity and rate per row, added and removed in the widget
    
        
    Rate
    Pre-filled from the item's cost price (purchase_rate), not the selling price, and still editable
    
        
    Status flow
    Draft → Submitted → Approved → Converted to Purchase Order, or Rejected, Closed, Void
    
        
    Scope
    Create-only by design: no list or edit path, so records can't be changed from the tab
